# AP6412 借晴制作与证据计划

建议采用路线 B，用现有 Godot C# 灰盒做成一个完整的 2D 关卡，冻结 `2d-baseline` 后，再用同一套规则做一个可独立运行的 Godot C# 3D 版本。两版都先为山阴村借光，再用原来升塔的雨水驱动货车，把一箱水果送到交付站。现有 Unity L5 作为早期设计来源，在报告里交代其先于本次课程移植的时间关系。

新版作业说明允许选择任意引擎及其支持的语言。建议两版都用 Godot C#，这样可以直接展示领域代码的复用，并减少引擎差异对移植分析的干扰。作业说明第 4 节要求先完成并冻结 2D，再实现同一游戏的 3D。内部灰盒可以有多个迭代，正式交付需要 2D、3D 两个可运行版本及标签。若小组考虑用已有 Unity 工程作为课程 3D 的底稿，跨引擎与既有实现的使用范围应先由老师确认。

## 两版共用的玩法合同

玩家从西侧低岸步行上塔。雨水蓄满后升至高位，机械锁保高。用风接北侧采光庭，走过去把采日镜调到接力位，再施晴让真实光线打到塔镜。沿北桥回塔，再转到东侧货轨位，塔镜将第二段光送入接光盘。村庄持续受光后出现一箱水果，原先蓄下的雨水进入运输配重。满足发车条件后登车跨谷，到站确认交付 `1/1`。采光庭是中途里程碑。

两版保留相同的停靠顺序、雨水用途、光路门槛、发车条件、结束判定和恢复规则。光线按实际镜面与遮挡求交。发车前失光时暂停转水和发车许可，保留已经转入配重的水和机械锁状态。已发车的货车继续到站，光路只约束待发阶段。落水回安全点，`R` 全局重开。范围控制在雨、风、晴和一次短交付，船鱼、修镜长对白、鹿岛等留在 Unity 原型。2D 采用侧视剖面，3D 采用实际空间转台和较固定的观察镜头。

| 轮次 | 实现与设计问题 | 过关条件和该轮证据 |
| --- | --- | --- |
| 00 · 塔台灰盒，已完成 | 西岸上塔、雨升、风接北桥、步行到旗标。记录为什么用单屏剖面，以及雨决定高度、风决定接岸的分工。 | 引用已有运行原帧、失败日志与复位修复。标为内部灰盒，实际 Git 历史从团队建仓时开始。 |
| 01 · 三岸能来回 | 给东侧加真实岸面与桥碰撞，补第三停点与明确转向。北侧旗标改成里程碑，玩家从北庭回到塔上再换接东岸。 | 从入口实走西→塔→北→塔→东。复测实体缺口、门槛拒转和 `R` 后再次过低桥。[本轮设计与验收](ROUND_01.md) |
| 02 · 让日光走完整条路 | 北庭风调镜、晴开放来光。用真实求交确认采日镜、塔镜和东岸接光盘的两段反射。 | 北向只有塔镜命中，东向且无遮挡才接光。复测偏转、实体遮挡和 `R` 后过低桥。 [本轮设计与验收](ROUND_02.md) |
| 03 · 同一份水送出一箱水果 | 做水果奖励、储水转配重、短货车行程和到站交付。水量变化与发车前置要从画面读得出来。 | 从 `R` 后连续操作到交付 `1/1`。验证储水减量等于配重增量、转水期间塔高不变、配重未满或实时光路断开时无法发车、交付只记一次。留完整路线和一组失光前后证据。 |
| 04 · 冻结完整 2D | 补开始说明、操作提示和必要视觉区分，做一次独立首次试玩或注明待测。按统一用例复测，完成 2D Class Map、README、核心类清单。 | 从干净检出能开局、完成、重开再完成。记录可运行提交及 GitHub 链接，冻结为 `2d-baseline`。 |
| 05 · 冻结后做 3D | 新建对等的 3D 场景，先接角色和塔桥，再接三维光学和货运。沿用能直接复用的 C# 规则和同一组验收用例。 | 逐项跑 2D/3D 对照，展示相同结果和一个无效操作。更新 3D Class Map，完成变化图、CCR、干净检出复测，标记 `3d-final`。 |
| 06 · 报告、演示和打包 | 从实际提交和证据写共同 PDF，补每人署名反思、AI 交流索引与声明。用提交版本彩排。 | 两个版本和必要资源可从交付说明定位，GitHub 对照链接可访问。组内每人讲自己的贡献。由一人按 NTULearn 的截止时间提交 `AP6412_GroupXX.zip`。 |

第 02 轮接通了北镜、塔镜和东盘。第 03 轮可以直接读取当前受光状态，验证失光时的转水与发车条件。

## 先把代码边界定住

`TowerMechanism` 持有水量、机械锁和停靠，`RouteProgress` 持有旗标顺序。`TowerSlice` 按设备分发输入，`TowerRig2D` 同步升降和桥碰撞。`SunCourtOptics2D` 管北庭日照和镜面，调用纯 C# `Optics2D` 求解。`SlicePlayer` 负责碰撞移动，`TowerView` 读取同一份光路和状态绘制。 [对象关系图](RELATIONSHIP_MAP.svg) · [现有场景协调](../../Scripts/TowerSlice.cs)

| 层与职责 | 什么时候动 | 3D 对应做法 |
| --- | --- | --- |
| `TowerMechanism` 持有塔与同一份雨水 | 01 补停靠和方向，03 再加入储水与配重的等量转移。 | 优先共享同一份 C# 源码。规则提供岸口身份和转向状态，各场景把它们映射为空间角度、桥位置和碰撞。 |
| 采日镜与接收规则持有局部天气、已校准和连续有效受光 | 02 有了第二个施令目标才加入。塔与北镜按目标分别响应。 | 共享接收时序、失光处理和奖励规则。让两版分别给出实际光路是否命中。 |
| `Optics2D` 计算有限镜面、反射和遮挡 | 02 新增二维几何求解。返回光段和命中结果，画面按该结果绘制。 | 3D 阶段再实现三维孔径与遮挡。沿用近交点、有限反射、需经过塔镜等规则和同一组正反例。 |
| 交付状态持有待发、运行、到站与完成 | 03 新增。由它检查发车条件并记录一次交付，实体载具由场景移动。 | 共享发车和完成判定，3D 场景自行接车轨、角色与镜头。 |
| `TowerSlice`、`TowerRig2D`、`SlicePlayer`、`TowerView` 管输入、场景与显示 | 每轮按需要接一组真实节点。现有调度继续使用，世界坐标和碰撞留在场景侧。 | 用 3D 节点承接角色、桥、光束和镜头。只有出现两个真实实现且共有契约清晰时，再决定是否提取接口。 |

## 每轮怎么留记录

开工前在个人分支记录本轮要验证的一件事、预期与负责人。提交时附实际运行方式、结果、截图或短视频。复核人用相同输入复跑，保存 PR 或合并记录。Figma 的现有四张灰盒画板保留为历史。后续每轮追加一张过程卡即可，左侧放前后或正反画面，右侧写决策和证据链接。只有代码职责或关系变了才更新 Class Map，报告里的最终类图以对应标签的真实代码为准。

```text
轮次 / 日期 / 主做和复核人 / 个人分支
要验证的玩家判断 / 开工前预期
实际修改 / 设计取舍 / 新增、修改、删除、不变的类及原因
实测版本、起始状态、输入、实际结果 / 成功和无效操作
观察或失败 → 修复 → 用同一用例复测 / 尚未验证项
提交或 PR / Figma 节点 / 日志或录像 / 相关 AI 原始交流位置
```

第一条可以直接用现有事实。`R` 后角色回到了低岸，但低桥碰撞留在高处，第二趟走不上塔。修复后用相同键码重新走，并补测运动中按 `R`。首次内置路线检查了重置后的初始状态，独立键码路线发现了真正的回归。保留两份证据及其范围，不补造当时的提交或试玩反馈。 [现有迭代记录](../ITERATIONS.md) · [失败、诊断和复测](../TESTING.md) · [Figma 灰盒过程板](https://www.figma.com/design/UINwS4sIWy2BFhFRFcJ0pB/ntu?node-id=471-55)

从建仓当天起，每位成员用可识别的个人分支，保存真实提交与 PR 或合并历史。完整保留按时间排列的 AI 提问、回复、修改与纠正，另用短索引指明哪些影响了设计或代码、成员如何核对。每人自己保留反思材料。未使用 AI 的成员按简报声明。

## 冻结后的比较和交付

在 `2d-baseline` 时先记下核心类名单与职责。建议用 `CCR = (移植中行为被修改或移除的 2D 核心类数) / (冻结的 2D 核心类总数) × 100%`，并单列 3D 新增的核心类。只移动文件或改排版单独标注。变化图逐项写共享、修改、新增、删除和理由，并链接实际提交。两版在不同目录时也要按职责对应逐类核对。简报要求解释本组算法，未规定统一公式或阈值。

约 15 分钟的现场可按 1 分钟讲游戏和控制、4 分钟跑 2D、4 分钟跑 3D、3 分钟讲类图与变化图、3 分钟展示测试和 GitHub/AI 证据分配。两版用同一组情景。正例走到交付，反例展示桥或光的无效条件，说明玩家怎样恢复。组内每人讲自己的设计或实现。报告用一份共同 PDF，分列概念、原始设计与假设、类图、扩展分析、实现与验证、GitHub/AI 证据和各成员署名反思。ZIP 附可运行工程与依赖说明、共同 PDF、组签原创声明和每人的生成式 AI 声明表。
