# 《借晴》小组工程规范

## 拿到工程后

- 用 **Godot 4.7.1 .NET** 和 **.NET 8 SDK** 打开 `BorrowingSun2D`，在 Godot 导入 `project.godot` 后按 F5。当前工程使用 Compatibility 渲染，C# 目标是 `net8.0`。引擎、SDK 或包版本变化单开任务，由组员确认后更新运行说明。 [工程入口](../../project.godot) · [C# 项目](../../BorrowingSun2D.csproj)
- 在 macOS 终端用临时副本验证时，先用 `cd -P` 进入工程的真实目录，从这里构建并启动。实测混用 `/tmp` 和 `/private/tmp` 会让构建出的 C# 脚本路径与场景引用不一致。
- 给同学的起步包包含完整 `BorrowingSun2D` 源码、配置、场景、资源及其 UID、运行和测试说明，以及可核对的基线证据。第 01 轮在塔台灰盒基础上完成北庭回塔再换接东岸的路线。 [操作说明](../../README.md) · [当前版本](CURRENT_STATUS.md) · [制作计划](PRODUCTION_PLAN.md)

## 代码和场景的职责

| 当前入口 | 负责的事 |
| --- | --- |
| [`Scripts/Core/TowerMechanism.cs`](../../Scripts/Core/TowerMechanism.cs) | 纯 C# 持有存水、台高、锁扣、风向、天气与停靠。外部用 `Cast`、`Recall`、`ToggleDrain`、`Tick` 和 `Reset` 变更状态，读取 `TowerState` 快照。 |
| [`RouteProgress.cs`](../../Scripts/Core/RouteProgress.cs) | 纯 C# 持有北庭到访与东岸完成，通过 `Visit` 和 `Reset` 更新。 |
| [`TowerSlice.cs`](../../Scripts/TowerSlice.cs) | 读取输入和玩家落脚，协调机关、实体同步、到访、恢复与复位。 |
| [`TowerRig2D.cs`](../../Scripts/TowerRig2D.cs) 与 [`TowerSlice.tscn`](../../Scenes/TowerSlice.tscn) | 场景保存岸、塔台、桥舌和旗标；适配器绑定几何，把机关状态同步成真实台高和桥碰撞。 |
| [`SunCourtOptics2D.cs`](../../Scripts/SunCourtOptics2D.cs) 与 [`Optics2D.cs`](../../Scripts/Core/Optics2D.cs) | 场景侧持有北庭天气和镜面调节，提供遮挡查询；纯 C# 求交并返回可供画面和玩法读取的实际光段。 |
| [`CargoJourney.cs`](../../Scripts/Core/CargoJourney.cs) 与 [`CargoTrack2D.cs`](../../Scripts/CargoTrack2D.cs) | 前者持有连续受光、装货和交付阶段，调用塔机转水；后者用行程进度移动实体车台。 |
| [`SlicePlayer.cs`](../../Scripts/SlicePlayer.cs) | `CharacterBody2D` 负责走路、落地和随活动台面移动。正常路线通过玩家输入和物理运动完成。 |
| [`TowerView.cs`](../../Scripts/TowerView.cs) | 读取快照和场景几何，绘制水箱、桥舌、朝向和操作反馈。 |
| [`TowerRouteCheck.cs`](../../Scripts/Verification/TowerRouteCheck.cs) | 用 Input Map 驱动生产场景，观察路径、碰撞、结果和重置。 |

- 给状态找一个拥有者。储水、配重及其等量转移放在同一套领域规则里。以后加入采光与交付时，局部天气和受光进度由采光组件持有，载具的待发、行驶、抵达和交付由运输规则持有。`TowerSlice` 负责组装这些职责，画面读取结果。先沿用现有结构，独立变化的职责出现后再拆分。
- 可复用的核心 C# 用统一的玩法单位、只读值和明确的操作结果，保持独立于 Godot 节点、输入、像素坐标与物理查询。做 3D 时优先共用水量、升降、停靠、奖励和发车规则。二维和三维各自接入角色、实体桥、空间查询、镜头与光路几何。确实需要第二套实现时，再提取两边已有的共同契约。 [两版玩法与移植计划](PRODUCTION_PLAN.md)

## 命名与编辑场景

- 沿用 `BorrowingSun2D`、`BorrowingSun2D.Core` 命名空间。类型、C# 文件和可读的场景节点名用 `PascalCase`，私有字段与局部变量沿用 `camelCase`，Input Map 动作用 `snake_case`。一个 Godot 脚本文件与挂载类保持同名。新增输入动作时同步更新操作提示、README 和受影响用例。
- `.tscn` 是实体位置、碰撞和引用的依据。改节点名、层级、文件名或目录时，检查 `GetNode` 路径、场景外部资源引用和主场景入口。在 Godot 的文件系统面板移动资源，保留并提交已有的 `.uid` 或其他序列化资源标识。每次提交核对 `.tscn` 差异，打开受影响的场景确认脚本和资源仍挂在正确对象上。
- 同一场景并行修改前先划分节点范围。改碰撞时对照实体桥和 HUD，改视觉时保留两者对同一实际几何的读取。记录哪几个文件随该改动一起保存，方便组员复跑或回退。 [当前作者场景](../../Scenes/TowerSlice.tscn)

## 玩法约束

- **接岸由真实承托决定。** 只在台面停稳、高度和朝向都对上时启用对应桥的碰撞。门槛占用要挡住转向，升降中拒绝风令。用实体路面验证通过和缺口。收令保留已有水量和朝向，到高位由机械锁保高。
- **光路由实际求交决定。** 光学求解器按镜面位置、有限孔径、法线与遮挡算出每段射线，接光盘需要正面命中。画面与货运读取同一份实时受光结果。发车后的行程按时间推进。
- **`R` 走统一复位入口。** 重置天气、机关、真实碰撞、玩家、安全点和完成状态，扩展后把光路、奖励、配重及载具一并纳入。平时升降和复位共用 `TowerRig2D.Synchronize()`。既有问题曾使节点看似回到低位，物理桥仍在高位，因此复位后必须重新走过实体低桥。 [复位实现](../../Scripts/TowerSlice.cs) · [碰撞诊断和回归](../TESTING.md)

## 每次交付给组员前

1. 编译后用正式场景从默认入口走一遍本轮修改的路线。当前最小回归包含上低桥、雨升随台、运动中拒风、门槛拒转、缺桥失足恢复、风接桥后实走到旗标、高位及运动中 `R` 后再次走过低桥。
2. 新增玩法要补成功和失效各一条。光路测遮挡、错面或错位时接光失败。运输测配重未满或失光时拒发车，到站后只记一次交付。摆位夹具单独标记，完整路线用生产输入和默认起点。
3. 记录日期、版本或真实提交、引擎和平台、起始状态、操作方式、预期与实测、退出结果和未测范围。保留失败、诊断及同一用例的复测。无头日志证明实际跑过的规则与碰撞，窗口原帧记录显示结果，首次玩家观察另列。 [当前测试命令和证据](ROUND_03.md) · [迭代实例](../ITERATIONS.md)
