# 2D 范围与决策登记 / Scope & Decisions

单人、单个连续短关卡，采用 Godot 4.7.1 .NET、C#、net8.0 和 Compatibility 渲染。2D 用单屏侧视剖面表达三岸、塔台与光路。先完成 Round 04 并冻结 2D，再做保持相同玩法的 Godot 3D。既有 Unity L5 是前期设计参考。 [游戏构思](DESIGN.md) · [制作计划](PRODUCTION_PLAN.md)

## Round 03 生产行为

西岸上塔 → 雨升并锁高 → 风接北桥 → 北庭调镜施晴 → 回塔转东 → 双镜送光到接光盘 → 连续受光装一箱水果 → 原水自动转配重 → 登车发车 → 到站下车确认交付 `1/1`。北庭与东岸旗标记录步行里程碑，花庭交付站记录货运终点。 [实际操作与测试](ROUND_03.md)

| ID | 决策 | 玩家能看到的结果 |
|---|---|---|
| D01 | 2D 顺序为三岸、光路、货运、体验收束与冻结 | Round 03 可跑完整主线，Round 04 继续做教程、视觉和冻结验收。 |
| D02 | 2D 使用侧视剖面；3D 的固定斜视为待验证方向 | 高度与接岸在 2D 同屏可见。两版保持同一套通行和接光规则。 |
| D03 | 塔上风令 `E` 顺转一档，`Shift+E` 逆转一档 | 西、北、东是可读停点；高位停稳才接通对应实体桥。 |
| D04 | 北庭采日镜有待机位和校准位；用风调镜再施晴 | 实际有限镜面和遮挡决定光路。北向命中塔镜，东向且光路畅通时才命中接光盘正面。 |
| D05 | 塔和北庭各自持有天气，`Q` 按站位收令 | 北庭晴天离开后继续生效。北庭设备旁 `Q` 清当地天气，其他位置 `Q` 收塔令。 |
| D06 | 装货前连续受光 1.5 秒 | 中途断光重新计时；装好的水果保留到交付或重开。 |
| D07 | 东向停稳、已有水果且实时接光时，原水自动转入配重 | 断光暂停，已转水量保留；复光从原进度继续。 |
| D08 | `TowerMechanism` 持有同一份雨水，机械锁维持高位 | 6 单位水分成塔箱 2 和配重 4；转水后限制排水。 |
| D09 | 站在实体车台上按 `G`，按五项条件发车 | 检查水果、实时来光、东向接轨、配重满 4 和乘车站位；拒绝时提示原因。 |
| D10 | 发车后按行程时间推进，行车中限制主动移动 | 碰撞承托角色；若失足，回到对应安全位置。发车后遇断光仍到站。 |
| D11 | 到站下车后走到花庭旗标，按 `G` 确认交付 | 交付计数从 0 到 1，重复操作保持 1。 |
| D12 | `R` 重开，平时失足则恢复到有效安全点 | 重开统一复位塔、桥、天气、光路、水、车和进度，再走低桥。 |
| D13 | Round 04 补开始说明、就地提示和结束反馈 | 重点观察雨升、接桥、调镜和发车条件能否被首次玩家读懂。 |
| D14 | 两版用同一组成功和失败用例复测 | 引擎适配可以不同，冻结时保留实测版本和差异。 |
| D15 | 场景、类图、测试说明和贡献证据跟随仓库 | 交接从可运行源码和对应版本证据出发。 |
| D16 | Windows x64 和 macOS arm64 是团队验证目标 | 各平台用对应版本的真实日志，见验收矩阵。 |

## 体验与取舍

约 **180 秒**是熟悉路线的设计目标，150–210 秒是最初的调优参考。该数字用来检查操作负担和等待节奏，真人实测、首玩理解和实际用时在 Round 04 单独记录。范围保留雨、风、晴和一次交付，船鱼、鹿岛和长对白留在旧 Unity 参考。 [参数与原始时间预算](NUMERIC_DECISIONS.md) · [验收用例](ACCEPTANCE.md)
